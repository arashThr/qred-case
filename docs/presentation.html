Definition of Ready

A story enters the sprint only once its contract is merged and the mock is live.

Why this scales

Less experienced devs fill in a known shape (a template and Zod). A senior reviews one PR instead of writing every spec.

Example from this case

"5 400 / 10 000 kr": used or left? We settle it in discovery, not in code review.

Keeping the contract honest

One source of truth, checked by machines

Non-breaking: add an optional field, add an endpoint, add an enum value FE already handles.

Breaking: remove, rename, or retype a field; change status codes. Needs /v2 or a deprecation window.

Domain model

Relational Postgres: constraints, joins, one consistent read

Money as integer öre + currency. No floats, no formatted strings.

No PAN stored, last4 only. Index on (company_id, occurred_at desc, id desc).

Used spend is computed from rows, never stored, so it can't drift.

The distinction that matters

Transactions, spend and invoice are three different things

TransactionSpend (widget)Invoice (banner)
WhatOne ledger entryUsed this period vs the user-set limitMonthly statement
When it existsAs soon as it happensComputed on every readWhen the billing cycle closes
SourceRowSUM of this period's rows, excluding reversedRow; txns get invoice_id at close
On homeLatest 3, all statuses5 400 / 10 000 krOldest unpaid, or null

Common mistake: treating the home list as "lines on the current invoice". A purchase made today is on the home screen now, but only on an invoice after the cycle closes. So the dashboard never filters by invoice_id.

API structure

Everything scoped under the company

Path under /api/v1Serves
GET/companiesCompany switcher
GET/companies/:companyId/dashboardThe whole home screen, one call
GET/companies/:companyId/cards/:cardIdCard chevron
POST/companies/:companyId/cards/:cardId/activateActivate card, idempotent
GET/companies/:companyId/invoices/:invoiceIdInvoice-due chevron
GET/companies/:companyId/transactions?cursor&limit"54 more items" (keyset cursor)

One membership check on :companyId guards the whole tree → 403.

Foreign ids → 404: a card from another company doesn't leak that it exists.

One error shape: { error: { code, message } }, and 400/401/403/404/409.

Why an aggregate endpoint

A BFF for mobile: one round-trip, one snapshot

  • Network: one request on a mobile connection
  • Consistency: used spend and latest txns come from the same snapshot
  • Decoupling: FE isn't tied to our internal resource split
  • Server-driven UI: BE decides actions.activateCard.enabled

Money is an object

{ minor, currency }. FE formats it with Intl.NumberFormat.

Empty states are in the contract

invoiceDue, card and spend can be null; latest can be [].

No maths on the client

remaining and remainingCount are computed server-side.

Actions, not status checks

FE renders enabled. Rules stay in one place.

Details that make it production-minded

Correctness under real conditions

Idempotent activation

One conditional statement:
UPDATE … WHERE status='pending_activation'
A double tap → 200 with the same body. Blocked → 409.

Keyset pagination

Opaque cursor (occurred_at, id). Stable under inserts, O(log n) with the index, unlike OFFSET.

Snapshot reads

Dashboard queries share one read-only REPEATABLE READ transaction, so the numbers never disagree.

Demo that never breaks

Seed dates are relative to now, so the view matches on any day. Tests run on a real Postgres via Testcontainers.

Contract check in every test

Each 200 body is parsed with its Zod response schema. If the implementation drifts from the spec, the test fails.

Isolation

One Postgres 18 container per file, reseeded before each test. No shared state with the dev DB.
